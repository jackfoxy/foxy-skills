# Command Reference

Every command runs from the repo root unless noted.

## Deploy to a ship

The desk is `desk/` with `desk.bill = :~ %tla-lus ==` and `sys.kelvin =
[%zuse 411 410 409 408]`.

```
::  on the ship
|new-desk %tla-lus
```
```bash
# from the host, into the ship's pier
cp -r desk/* /path/to/pier/tla-lus/
```
```
::  back on the ship
|commit %tla-lus
|install our %tla-lus
|start %tla-lus
```

For an already-installed desk, `|commit %tla-lus` after a copy is enough —
Gall reloads the agent and `on-load` **coerces** the stored state (`;;` inside
`mule`), so completed jobs survive a mold change. An in-flight job resumes from
its persisted cursor to a byte-identical result.

`|nuke %tla-lus` then `|start %tla-lus` restarts the agent; state survives.
Only `|uninstall` discards it.

## The two halves of tier 1 — run on every change

```bash
python3 tools/validate.py --check      # goldens reproduce byte-identically from the pin
```
```
-test /=tla-lus=/tests ~               # on the ship; expect ok=%.y
```

`validate.py --check` recompiles the oracle dumpers (`tools/oracle/*.java`),
reruns every generator, and hashes the oracle-derived trees before and after.
It **refuses to regenerate** if the `tlaplus` checkout is off-pin, so a golden
cannot silently drift to a newer tool version.

The Hoon suite runs the generated differential shards plus the hand-written
property suites: `crc`, `sim`, `job`, `bnf`, `diagnostics`, migration, and the
`app` agent tests.

## Tier 2 — CI / nightly

```bash
python3 tools/tier2.py --check         # inventory + curated oracle reproduce
python3 tools/gen-tier2-tests.py       # regenerate its goldens
python3 tools/tier2-select.py          # pick a subset
```

Corpora: `tlaplus/test-model` (175 specs) and the `tlaplus-Examples` matrix,
classified from the repo's own `manifest.json`s. Every module lands in
`sany`, `check`, or `excluded:<reason>` in
`desk/test-data/tier2/inventory.txt`; the classification rules are **total**,
so an upstream-added spec drifts the frozen inventory and `--check` catches it.

## Tier 3 — a performance report, never a gate

```bash
python3 tools/tier3-report.py          # each workload against desk/test-data/perf/baseline.json
python3 tools/tier3-noise.py
bash tools/release-gate.sh --tier3     # the gates plus the report; still never fails on it
```

It exits nonzero **only when the shard itself fails** — a changed work profile,
which is an ordinary test failure, not a performance signal. R2.8.1a measured
run-to-run spread at 15.6% on a fresh boot, over its own ±15% bar, so a
threshold here would fail runs for being on a busy machine. Promoting this to a
gate needs a **new measurement**, not a new opinion.

## The gates

```bash
bash tools/scaffold-gate.sh            # 11 gates: hygiene, NOT parity
bash tools/release-gate.sh             # the real one
python3 tools/check-parity.py          # ledger well-formed + owed count
python3 tools/check-portmap.py         # ledger <-> port-map coherence (scaffold gate 10)
python3 tools/r3-acceptance.py --suite-log <captured suite output>
```

`scaffold-gate.sh` proves the pin, golden reproducibility, no Java/GUI,
provenance, kelvin, a migration mechanism, bounded fixtures, a desk manifest,
port-map/ledger coherence, and a well-formed ledger. **It passes whatever the
ledger owes** — it reports the count and moves on.

`release-gate.sh` adds: **R1** ledger closed (zero partial/absent/oracle-only),
**R2** tier 2 green, **R3** no stubs or TODOs in port code (vendored upstream
text exempted), **R4** refusals documented **both ways**, **R5** upgrade/restart,
**R6** reproducible oracle artifacts. It cannot check the ship suite — run
`-test` yourself and feed the captured output to `r3-acceptance.py --suite-log`.

`r1-acceptance.py` still prints `R1 NOT ACCEPTED` and **must not be edited to
pass**: it is the record of what R1 proved, asserted against R1's closing
state, which is not the ledger R3 closed.

## Generators

One per differential area; all read fixtures from `desk/test-data/<stage>/` and
write shards into `desk/tests/lib/`.

```
gen-lexer-tests      gen-parser-tests      gen-parse-err-tests   gen-bnf-manifest
gen-modres-tests     gen-sem-tests         gen-cfg-tests         gen-cfg-val-tests
gen-eval-tests       gen-core-eval-tests   gen-stream-tests      gen-stdops-tests
gen-mc-tests         gen-safety-tests      gen-coverage-tests    gen-liveness-tests
gen-sim-tests        gen-sim-live-tests    gen-sim-stats-tests   gen-generate-tests
gen-dfid-tests       gen-rng-tests         gen-mp-tests          gen-perf-tests
gen-stdmods          gen-tier2-tests       gen-pcal-tests (oracle-only)
```

`desk/doc/evidence-counts.md` is **generated by `validate.py`** — cite it,
never hand-write a count.

## The Java oracle

```bash
cd $TLA_REPO/tlatools/org.lamport.tlatools
ant -f customBuild.xml info compile compile-test dist   # -> dist/tla2tools.jar
java -cp dist/tla2tools.jar tlc2.TLC -deadlock test-model/pcal/Bakery.tla
# must print: 1183 states generated, 668 distinct states found, depth 41, no error
```

`TLA_REPO` defaults to `/mnt/mars/gitrepos/tlaplus` in `scaffold-gate.sh`;
the pin is `4ba7d8811289fb8e95dac4d5e554c05216ba3100`. Determinism flags for
**every** oracle run: `-workers 1 -fp 0`, plus an explicit `-seed` for
simulation. See `tla-lus-parity` for the invocation forms and the
normalization rules.
