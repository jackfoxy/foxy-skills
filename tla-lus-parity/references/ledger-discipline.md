# The Parity Ledger

`desk/doc/parity-manifest.md` is the machine-checked ledger: **one row per Java
behavioural cluster** (granularity matching `port-map.md` §4) and **one row per
public request option**. `tools/check-parity.py --check` fails if any status is
blank or not one of the closed set, so nothing in scope stays unclassified.

## Statuses

| Status | Means |
|---|---|
| `parity` | Hoon behaviour differentially matches the pinned Java oracle |
| `partial` | a first increment matches a narrow slice; named behaviour is still missing |
| `approved-difference` | a deliberate, documented divergence, **tested as such** |
| `replaced` | the Java mechanism is intentionally supplanted by a Hoon/Gall one; no byte parity is meaningful |
| `absent` | in scope, not yet implemented |
| `excluded` | out of scope per the plan; the rationale states why |
| `oracle-only` | goldens captured from the pin, but no Hoon comparator exists yet |

**`oracle-only` proves nothing about parity** until a comparator lands. Two
generators are in that state: `gen-pcal-tests` (2 cases) and
`gen-safety-tests`'s 20, whose comparators live in other shards.

## What a row does and does not claim

- A `parity` row means a differential comparator agrees with the pin **on that
  row's projection** — not that every conceivable behaviour was compared.
- An `approved-difference` row means the port deliberately differs, the
  difference is **stated**, and a test pins it. `tools/check-portmap.py` fails
  if one is added to the ledger without appearing in `compatibility.md`.
- The **scaffold gate proves hygiene, not parity.** It reports the owed count
  and passes anyway.

## Cite counts, never write them

`desk/doc/evidence-counts.md` is **generated by `tools/validate.py`**. Every
count in every document comes from there. Currently: **1277 compared cases, 22
oracle-only**, plus 14 end-to-end goldens in the oracle baseline outside the
table.

## History worth knowing

- **R1 closed the ledger at 125 rows**, all terminal, and
  `tools/r1-acceptance.py` recorded that (4/4 clauses, release gate PASS, ship
  suite `ok=%.y`).
- **R2.0 deliberately re-opened it.** R2 widened scope — Clay write-back, DFID,
  `TLCGet`/`TLCSet`, `Randomization`, non-debugger `TLCExt`, four config
  capabilities that had been typed rejections (`VIEW`, `ALIAS`, cfg source
  override, `INVARIANT`+`PROPERTY` together), the driver surface re-decided as
  capability rather than CLI — and **withdrew approval from seven differences**.
  Two rows were new (`cfg-view`, `cfg-alias`). A red release gate was R2's
  *intended* state.
- The count rose to 134 at R2.7.7.0, which was **not drift**: three rows were
  *created* for `.cfg` keywords no row had ever covered (`cfg-postcondition`,
  `cfg-possible`, `cfg-internal-kw`).
- **R2.8.2b re-opened three rows on measurement** and handed them to R3.
  `tlc-eval-node` (a `LAMBDA` operator-valued argument), `tlc-eval-action` (a
  multi-binder existential in action position) and `cfg-runspec` (a config with
  no behaviour spec) — **all three found by the first `tlaplus-Examples` specs
  ever run through the Hoon checker**, none reachable from any spec the corpus
  already ran.
- **R3.0d closed the last one.** `SubsetEnumerator.reset()` rewinds without
  reseeding, so every draw happens at construction in group order and an inner
  group replays its permutation; the port draws once per group and walks a fixed
  odometer, proven by 30 seeded exact-trace cases.
- **R3.2 demoted `tlc-value-composite` on a wrong answer** — a RECORD does not
  compare equal to a FUNCTION — found by adding `BagsTest` to the batch, where
  exactly the 6 assumptions with a record-literal expectation failed. **That
  row's evidence compared renderings, and a rendering differential cannot see
  an equality.** R3.2a closed it the same day (`+fcn-like` now admits `%rec`,
  which `+to-fcn-pairs` four lines below had always done) and fixed a second,
  latent divergence: record form in rendering is tlc2's `isName`, not "the
  domain is all strings".

**Current: 134 rows, 134 terminal, 0 owed — closed 2026-09-05.**

## The four lessons this history encodes

1. **Read a red gate's other clauses.** `release-gate.sh` was red by design for
   the whole of R2; behind the clause everybody knew about, a `TODO` token and
   **eleven undocumented refusals** rotted unseen.
2. **A projection that does not look at something cannot report it as
   agreeing.** Rendering differentials cannot see equalities; a comparator that
   captures trace lines only after the counter-example markers cannot see an
   initial-state violation's trace.
3. **New corpora find new rows.** Three rows re-opened the first time
   `tlaplus-Examples` specs were run. Widening the input is a measurement, not
   a formality.
4. **Do not edit an acceptance script to pass.** `r1-acceptance.py` still prints
   `R1 NOT ACCEPTED`, correctly — the ledger it asserts is not the one R3
   closed.

## Adding or changing a row

1. Read the existing row's rationale first; it usually explains why the shape
   is what it is.
2. **Measure the pin before changing the Hoon.** Most of this port's expensive
   mistakes were assumptions about tlc2 that measurement contradicted — a flag
   whose documented effect was backwards, a "timing" difference that was
   actually a verdict difference, a "recursion" gap that had shipped two
   releases earlier.
3. If the behaviour will deviate, write the `compatibility.md` entry **with its
   evidence generator** before shipping. `release-gate.sh` R4 checks refusals in
   both directions.
4. Keep `port-map.md` coherent — `tools/check-portmap.py` is scaffold gate 10.
5. Regenerate `evidence-counts.md` by running `validate.py`; never hand-edit a
   count.
